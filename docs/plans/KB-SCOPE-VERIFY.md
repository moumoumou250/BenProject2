# KB 聚焦检索验证方案：先验知识可达，再按缺口类型补

状态：待评审（未执行）
日期：2026-11-18
范围：`ben/kb/` + `ben/commands/kb_cmds.py` + `ben/cli.py` + `ben/kb/entries/*.json`
约束：只改检索与命令面；不动 `Store` / fact graph / 默认检索行为

---

## 0. 我对需求的理解

要解决的是**知识可达性**问题，不是漏洞检测问题。两者必须分开：

| | 含义 | 本方案是否覆盖 |
|---|---|---|
| **A. 知识命中** | KB 里有没有、能不能检索到这条漏洞的打法 | ✅ 本方案 |
| **B. 漏洞命中** | 拿真实目标，能不能真打出这个洞 | ❌ 不属于本方案 |

A 是 B 的**必要条件**：KB 检索不到，agent 大概率打不出；但检索得到 ≠ 一定打得出。

因此本方案的输出只能是「**知识可达 / 不可达**」，绝不能说「漏洞有 / 没有」。

需求分两段：

```
第一段  验：给定「漏洞 + KB scope + 查询词」，判断范围内能否检索到该漏洞的知识
第二段  补：检索不到时，先判缺口类型，再用最小成本补对，然后用同一入口回归
```

---

## 1. 目标 / 非目标

| | 内容 |
|---|---|
| 目标 | 一个**限定范围**的 KB 检索入口：范围外的条目完全不参与匹配；未命中时能区分「词表缺口」与「内容缺口」 |
| 非目标（本次不做） | 漏洞实际探测、PoC 执行、报告渲染、ben 调度集成、命名 scope 组、向量检索 |

---

## 2. 核心原则：硬约束，不是软排序

这是最容易做错的地方。

```
❌ 错：范围外条目也参与打分，只是排后面 —— token 重叠仍可能把它顶上来
✅ 对：候选集在打分之前截断，范围外条目根本不进入计算
```

现有 `KnowledgeBase.search()` 的 tag 过滤已经是这个模式（先 `continue` 跳过、再打分）。`only` 复用同一位置，不新增排序权重。

---

## 3. 改动落点（三处，均为小改）

### 3.1 `ben/kb/__init__.py` → `KnowledgeBase.search()`

签名增加 `only: list[str] | None = None`：

| 取值 | 行为 |
|---|---|
| `only=None` | **行为逐字节不变**（向后兼容，现有测试与调用方零影响） |
| `only=[...]` | 仅在该 id 集合内检索；集合外的条目在打分前被跳过 |

### 3.2 `ben/commands/kb_cmds.py` → `cmd_kb()` 的 `search` 分支

- 解析 `--only`（支持重复与逗号）
- **校验每个 id 是否存在**，不存在即报错退出
- 传入 `search()`
- 多打一行 `scope:` 说明

### 3.3 `ben/cli.py` → `kb` 子命令

增加 `--only`，用 `action="append"`，与现有 `--tag` 保持一致的写法。

### 3.4 顺带确认的现存限制

`cmd_kb()` 现在是 `tag = args.tag[0]` —— **多个 `--tag` 只有第一个生效**。与 scope 相邻，建议一并确认是否为预期行为（本次不强制修）。

## 4. 命令面

```
ben kb search "<query>" --only kb002
ben kb search "<query>" --only kb001,kb002          # 逗号
ben kb search "<query>" --only kb001 --only kb002   # 重复
```

推荐的第一组 scope（SQL 注入方向）：

| scope | 包含 | 覆盖的能力 |
|---|---|---|
| 最小 | `kb002` | 只验「已知参数能不能打」 |
| **实用（推荐起点）** | `kb001` + `kb002` | 找参数（kb001 第 6 步）→ 打注入（kb002） |
| 完整 | `+ kb016` / `kb053` | 指纹定版本、批量验证 |

> 注意：只锁 `kb002` 会缺「去哪找注入点」这一环，导致 agent「会打但找不到靶」。

---

## 5. 输出与语义边界

### 5.1 输出形态

命中：

```
scope: kb002 (1 entry) — excluded 55
kb002  score=0.67  [web,sqli]  SQL 注入 — 确认、绕过与提数据
```

未命中：

```
scope: kb002 (1 entry) — excluded 55
(no match inside scope; 2 matches outside — run without --only to see them)
```

`scope:` 行不可省略 —— 它是「约束真的生效」的唯一凭证。

### 5.2 三种结果必须分开

| 结果 | 含义 | 行动 |
|---|---|---|
| 范围内命中 | KB 覆盖该漏洞 | 通过 |
| 范围内无命中，范围外有 | 知识在，但不在 scope | 调 scope，或条目该归并 |
| 范围内外都无 | KB 真缺这块 | 补内容 |

### 5.3 退出码

沿用项目既有约定（与 `tests/TestRange/rangectl.py` 一致）：

| 码 | 含义 |
|---|---|
| `0` | 范围内命中 |
| `1` | 范围内未命中 |
| `2` | 用法或范围错误（id 不存在、`--only` 为空等） |

### 5.4 必须定死的两个错误语义

- **id 不存在 → 报错退出（2）**，并列出可用 id；**禁止静默忽略**（静默会让 scope 名存实亡）
- **`--only` 为空 → 用法错误（2）**，不当作「无命中」

## 6. 缺口判定：词表缺口 vs 内容缺口

`/`「检索不到」有两种，补法成本差一个数量级。判定方式是**同义变体成组跑**：

| 现象 | 缺口类型 | 补什么 | 成本 |
|---|---|---|---|
| 查 `二次注入` 不中，查 `second-order` 中 | 词表缺口 | 补 `tags` / `description` 措辞 | 低 |
| `二次注入` / `second-order` / `存储型注入` 全不中 | 内容缺口 | 新增或扩写条目 | 高 |

检索本质是 **token 重叠的词面匹配**（title ×2 + description + tags + detail 前 500 字）。因此「不命中」往往不是内容没有，而是**查询词没在条目里出现过**。

**这条判定是本案最有价值的输出**：它不评价「KB 好不好」，它告诉你「该用哪种方式补」。

---

## 7. 补充形态：只借 Strix 三样

仅在**内容缺口**时动内容。借 Strix skill 的结构，但不借它的体系。

### 7.1 借这三样

| 借什么 | 理由 | 落到 kb002 |
|---|---|---|
| **拆细**：一条讲透一件事 | 现在 kb002 一条塞了「确认 + 绕过 + 提数据」，深不下去 | 拆为：确认 / 绕过 / 提数据 / 二次注入 |
| **`validation` 字段** | 「怎么算命中、什么情况会误判」——当前 KB 完全没有，正是漏报/误报的根因 | 「布尔差异需基线对比；时间盲注需 >3× 网络抖动」 |
| **按子能力分节** | 让检索能落到小节，而非整条模糊命中 | `detail` 内分节，`tags` 补到子类 |

### 7.2 明确不借

- ❌ 5 篇注入上限
- ❌ 11 类目录树
- ❌ agent 专精（`create_agent(skills=...)`）

这三样服务于「多 agent 分工、每个只懂一点」。本项目是**单点聚焦、一个 agent 从头打到尾**，引入整套体系属过度设计，只增加维护成本。

### 7.3 闭环

```
① 验  ben kb search "二次注入" --only kb001,kb002   → exit 1
② 判  换同义变体再跑
        ├─ 某个变体中  → 词表缺口 → 补 tags/description → 回 ①
        └─ 全不中      → 内容缺口 → 进 ③
③ 补  拆细 + validation + 分节
④ 再验 同一查询重跑 → exit 0
```

## 8. 验收标准

针对 scope `kb001,kb002`：

### 8.1 正例必中

以下查询在 scope 内**均须命中 kb002**（exit 0）：

```
ben kb search "sql 注入"   --only kb001,kb002
ben kb search "布尔盲注"   --only kb001,kb002
ben kb search "报错注入"   --only kb001,kb002
ben kb search "union 注入" --only kb001,kb002
```

### 8.2 反例不中

```
ben kb search "文件上传" --only kb001,kb002   → 不应命中 sqli 条目
ben kb search "提权"     --only kb001,kb002   → 不应命中 sqli 条目
```

### 8.3 约束生效

```
ben kb search "文件上传" --only kb002
→ (no match inside scope; ... matches outside)  # 证明范围外条目被排除
```

### 8.4 错误路径

```
ben kb search "x" --only kb999     → scope error, 列出可用 id, exit 2
ben kb search "x" --only           → 用法错误, exit 2
```

### 8.5 兼容性

- 不带 `--only` 时，输出与改动前**完全一致**
- 现有测试全绿

## 9. 风险与取舍

| 风险 | 级别 | 说明 / 缓解 |
|---|---|---|
| 把「知识可达」误读成「漏洞可检出」 | **高** | 输出措辞严格区分；文档与 help 文本明确写「仅验证知识可达性」 |
| scope 过窄导致「会打但找不到靶」 | 中 | 推荐 scope 含前置能力条目（kb001）；文档给出三档 scope 参考 |
| 词表缺口被误判为内容缺口 | 中 | 强制「同义变体成组跑」，单次不命中不下结论 |
| 检索阈值过松，反例也命中 | 中 | `score` 输出可见；反例验收（§8.2）作为硬门槛 |
| 多 `--tag` 只有第一个生效 | 低 | 已知限制，本次仅确认、不强制修 |
